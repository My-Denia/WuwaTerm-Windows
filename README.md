# WuwaTerm 桌面客户端

面向 Windows 的鸣潮术语与双语稿件工作台。本地编辑和文件保存不需要服务连接；
查词、翻译和术语审校调用 HTTP 接口，词典查找、方向判定以及翻译流水线不会在客户端重新实现。

这是独立的 Windows 产品仓库，不属于服务端 wheel，也不发布到包索引。运行时通过 HTTP API 使用服务，客户端不安装服务端翻译规则。

界面语言是中文,且只有中文。

## 版本与接口兼容

当前版本 **0.4.2**(2026-11-12 发布,见下文「发布」一节的发布记录;下载步骤以它为例)。这是一次界面修复:未配置状态下术语页的标题/状态行与空状态卡片不再拉伸,查词区的 Tab 顺序按视觉顺序经过分类筛选。它有自己的版本号,与服务端的版本号分开走。

这个客户端说的是 HTTP 接口的 **`v1`** 版本 —— 也就是 `/v1/*` 这组路径,以及
`GET /v1/meta` 回复里的 `api_version` 字段。稿件审校还需要服务端支持 `review-v2`;语义审校和翻译
上下文只在 `GET /v1/capabilities` 列出时使用。Web 稿件互通使用 `wuwaterm-manuscript-v1`,有语义
数据时使用 `wuwaterm-manuscript-v2`;v2 稿件需要包含语义审校的 Web 版本才能打开。

两边对不对得上,由「服务状态」区那一次「刷新」顺带查出来:那次请求本来就要发,客户端
读回其中的 `api_version`,发现不是自己支持的版本时,就在同一块界面上给出提示,并写明
服务端报的是哪一版、这个客户端支持的是哪一版。版本、数据档位、术语条数等信息照常显示 ——
你需要看见那个对不上的版本号,把它藏起来毫无意义。程序也照常可用:**这是一条警告,不是
拒绝**,字段可能对不上比连话都不说要好办得多。

这项检查没有为自己多发一次请求:没有启动时的探测,没有定时轮询,也没有额外的请求头。
**你不开口,它就不会发出任何请求** —— 未配置状态下一个字节都不会出去,这一点由测试钉住
(`tests/test_api_version_compat.py`)。

## 获取与运行

可从 [WuwaTerm Windows Releases](https://github.com/My-Denia/WuwaTerm-Windows/releases) 下载便携压缩包及同次发布的 `SHA256SUMS`；也可按下文自行构建。

1. 下载 `WuwaTerm-0.4.2-windows-x64.zip` 和同一次发布的 `SHA256SUMS`。
2. 核对校验和，再解压：

```powershell
Get-FileHash .\WuwaTerm-0.4.2-windows-x64.zip -Algorithm SHA256
```

   将输出与 `SHA256SUMS` 中该文件的哈希比对，不一致时不要解压。

3. 解压到任意目录 —— 压缩包里就一个 `WuwaTerm` 目录,不会把几百个文件铺到当前位置。
   它是便携版,不写注册表,也没有安装程序;整个目录就是这个程序。
   但删掉这个目录并不等于删干净:设置文件留在 `%APPDATA%\WuwaTerm\config.json`,
   设备令牌留在 Windows 凭据管理器里。要彻底移除,先在程序里「设置 → 遗忘令牌」
   (或从凭据管理器删除 WuwaTerm 条目),再删掉那个设置文件,最后删目录。
4. 运行目录里的 `WuwaTerm.exe`。

**这个程序没有代码签名。** 首次运行时 Windows SmartScreen 会弹出一块蓝色提示,
默认只给一个「不运行」按钮;点其中的「更多信息」,再点「仍要运行」即可。这不是本项目
能靠改代码消除的提示:消除它需要一张付费的代码签名证书,而这是个业余项目,没有买。
如果你不接受这一点,请按下文「构建」在本机自行构建。

启动后可直接编辑、保存和重开本地稿件。在线查词、翻译和审校需要在设置中配置两样东西，均由服务运营方提供：

- **服务器地址**:已发布服务的基地址(`https://<主机名>[/<路径前缀>]`);如果服务就跑在你自己这台
  电脑上,则填 `http://127.0.0.1:8788`。规则见下文「配置服务器地址」。
- **设备令牌**:形如 `wtd1.<设备 id>.<密钥>`,由运营方用 `wuwaterm-api device issue`
  登记后带外交给你。没有自助注册。

两样都配好之后，在「术语查词」输入一个官方术语并按回车，才会发起查询。
缺少设备凭据的在线操作会在发送前拒绝，不会以匿名请求代替。

## 它能做什么

以下为 0.4.2 的能力;0.3.0 及更早的客户端包不含稿件内语义审校、翻译上下文与分段审校,请以对应发布说明为准。

- 通过共享的「词典优先」流水线翻译文本(`POST /v1/translations`),方向可自动判定,
  也可强制指定。
- 查询官方词典术语(`GET /v1/terms`),按「搜索」或回车发起。
- 本地保存和重开双语稿件,按需调用术语审校(`POST /v1/reviews`),定位并修订一处结果。
- 展示服务状态:版本、数据剖面、数据提交号、术语条数,以及是否配置了翻译模型
  (`GET /v1/meta`);同一份回复里的 `api_version` 会与本客户端支持的接口版本核对一次,
  对不上就在这一区给出提示。
- 在 Windows 凭据管理器中保存**一个**设备令牌(经 `keyring`)。该令牌不会写进配置
  文件,这个程序也从不以明文把它写到磁盘上的任何地方。

## 界面怎么用

左侧窄导航连接稿件、查词和翻译，设置在底部。默认进入稿件，两个可调编辑区旁是
可收起的上下文审校面板。服务诊断通过设置／菜单入口访问；原有快捷键继续保留：

| 区域 | 用途 | 快捷键 |
| --- | --- | --- |
| 术语查词 | 显式查询官方译名 | `Ctrl+1` |
| 文本翻译 | 整段文本翻译,可能调用模型 | `Ctrl+2` |
| 服务状态 | 服务端版本与数据信息 | `Ctrl+3` |
| 稿件审校 | 默认工作区，本地编辑、审校与保存双语稿件 | `Ctrl+4` |

`Ctrl+K` 把焦点移到当前区域的输入框。

服务配置状态保留在辅助信息与设置中，未配置服务不阻挡本地编辑。
“已配置”只表示保存了地址，不代表已经验证连通性；只有显式在线操作才会发送请求。
新界面的设计目标与历史取舍见 [设计记录](https://github.com/My-Denia/WuwaTerm/blob/cc5743df0e807c42e4b669564fd8b4d0a465b79c/docs/adr/0016-desktop-resonance-workbench.md)。

### 术语查词

**按「搜索」或按回车才会发起查询。** 这个客户端不做边打边搜:光是打字不会产生任何请求。

请求进行中「搜索」按钮变灰;回车绕过变灰的按钮直达处理逻辑,所以处理逻辑自身还会拒绝
第二次提交——同一时刻只有一次查询在路上,回复不会乱序覆盖。

两种情况下按下去也不发请求:输入为空,以及输入长到像一句话而不是一个术语(超过 40 个字
或含换行)。后一种会给出一张卡片说明这不是术语查询,并提供一个按钮把这段文字直接送到
文本翻译区。

查不到时,空结果卡上同样会给一个按钮,把刚才那个词送到文本翻译区并填好,不必重新输入。

查询失败时,上一次的结果行会被清空——留在原地会被读成这次查询的结果。失败的原因显示在
上方,请求 ID 留在下方,可以复制去问运营方。

更换服务器地址会清空结果表:词典属于某一个具体的服务,把一台服务器的答案留在另一台的
名字底下是错的。

> **不具备的行为**,写在这里以免被误以为有:没有防抖自动查询、没有查词结果缓存、
> 没有针对限流的自动退避或自动暂停。服务端因请求过密而拒绝时,界面会报告并给一个
> 「重试」按钮,由你决定何时再来。

### 稿件审校

在「稿件审校」中输入或粘贴原文和译文,选择译文方向后按「审校」(`Ctrl+Shift+R`),客户端
才会向已配置的服务发出请求。两侧均需有内容。审校需要服务端支持 `review-v2`;仅凭服务报告
`api_version: v1` 不能证明该能力可用。

每次审校先查询一次 `GET /v1/capabilities`。旧服务端对这个路径返回 404,客户端就只做原来的
术语审校,行为与 0.3.0 相同。服务端列出 `semantic-review-v1` 时,再按段请求语义审校。

语义审校是服务端的实验性开关,默认不开启;自托管可以显式开启。服务端没有列出它时(这是常态),
审校面板只有「术语约束」和「段落」两组,长稿照常按段审校并显示进度,不会出现空的语义分组。
列出时才多出「语义疑点」一组,带"实验性"标记。审校面板最多分三组:

- 「术语约束」:`/v1/reviews` 的确定性结果,只说明词面是否匹配官方形式,不调用模型。
- 「语义疑点」:模型提出的可能漏译、增译、否定或数量改变等疑点。它们可能有误,把握程度是
  模型自评,未经校准;没有列出的地方也不代表没有问题。
- 「段落」:长稿按 `segmentation-v1` 配对后的各段及其状态。

每条疑点只能逐条处理,没有"一键采纳全部":「采纳」(`Ctrl+Enter`)把建议写入译文,「调整」
(`Ctrl+Shift+E`)按你改过的文字替换,「忽略」(`Ctrl+Shift+I`)只做记录。处理后自动跳到下一条
待处理的疑点,`F8` / `Shift+F8` 也可前后切换。模型认为范围过长时不给可直接采纳的建议,只能
调整或忽略。采纳前会再核对一次:译文在该位置的文字必须与疑点记录的完全一致,否则不替换,
显示"需重新确认"。这三种处理都可以撤销和重做。编辑正文不会丢掉其他段落的疑点;改动过的
位置会标为需重新确认,翻译方向改变则清除全部语义疑点。

服务端提供语义审校或翻译上下文(`translation-context-v1`)时,稿件内翻译和语义审校默认都附带
本稿此前的人工判断作为先例,每条只说明那一处,不写进稿件;「更多操作」里的选项可以关掉。
这与 Web 工作台一致,依据是服务端评测中先例相关的两道门(同义沿用、被带偏)均已达标。

任一侧超过 2,000 字时,术语审校和语义审校都按段进行,每段每侧最多 1,800 字,一次只发一个
请求。无法可靠配对的段落标为"需要手动切分",不会发出请求;请在两侧对应位置插入空行后
重新审校。强制切分的段落会提示边界附近可能误判。服务暂时限额时审校会暂停并显示已完成的
段数,之后按「继续审校」只补审尚未完成的段落;未改动的段落不会重复发送。

已有的分段结果(术语报告、语义报告、失败与提示、在途请求的回复)只有同时满足两点才会沿用:
它的两侧位置与当前某个可发送的配对完全一致,且那里的文字仍是当初发送的版本、其间没有被编辑;
它的依据与现在完全一致,包括该段术语请求所带的段落对应、服务端是否提供语义审校(提供时必须有
完整的语义报告才算审完)以及合同版本(`review-v2`、`semantic-review-v1`)。每次审校开始时按当前
配对重建计划,其余结果一律丢弃;疑点的处理记录不随之丢弃,仍按出现位置规则处理。代码中的唯一
来源是 `semantic_session.Basis`。

译文为空时,「翻译」(`Ctrl+Shift+T`,译文标题栏的按钮)按段翻译原文并写入译文,段落之间的
空白原样保留;在「段落」中选中一段"尚未翻译"的段落,也可以只翻译这一段。已有的译文不会被
覆盖。服务端列出 `translation-context-v1` 时,每段会附上前一段的原文和译文作为只读上下文。

报告列出需要查看的位置和候选术语。选择一条发现可定位原文及译文中的对应位置;目标位置
不可用时需手动查看。在替换框中确认文本后,「替换这一处」只修改选中的译文位置。编辑正文
或改变方向后,旧报告会过期,需要重新审校;更换服务器地址也会使当前报告失效,但不会清空稿件。
审校检查术语约束和基础结构,不评估完整句意。

「撤销修订」和「重做」可处理最近 20 步稿件更改,包括正文编辑、单次替换、方向和段落对应
调整以及移除历史选择。在文本框中也可用 `Ctrl+Z` 撤销、`Ctrl+Shift+Z` 重做。这些操作
不回退后来追加的历史报告,也不改变当前保存路径或保存基线;撤销或重做后仍需重新审校。
如果输入法还有未确认的文字,先提交或取消该输入,再保存、切换稿件或关闭窗口。

如果导入的稿件带有明确的段落对应,修改正文或方向会清除旧对应,避免继续使用已经过期的位置。
此时不会悄悄推测新的对应关系;需要按句自动对应时,可以主动选择「使用自动对应」并重新审校。

「保存稿件」和「另存稿件」写入 UTF-8 JSON 工作稿,「打开稿件」可在以后恢复。没有语义审校
数据时格式为 `wuwaterm-manuscript-v1`,可与公共 Web 的稿件文件互通;有语义处理记录或语义报告
时写为 `wuwaterm-manuscript-v2`(格式由公共 Web 的 `docs/manuscript-v2.md` 定义,两端互读),额外保存
最多 128 条处理记录、"忽略"记录复审时需要的最多 16 份旧正文,以及最近 2 次语义审校的报告(仅作
历史参考)。单个文件上限为 1 MiB;超出时先丢最旧的语义报告,处理记录一条也不丢。重新审校时,
上次的"忽略"只有在两侧位置都能在旧正文中唯一恢复、且新报告里恰好有一条同类疑点落在该处时
才自动沿用;旧正文缺失或校验不符等其余情况显示为需重新确认,处理记录保留。曾经采纳过的位置
再次被报告时会注明。导入时界面
提示历史报告及待核对选择的数量,保留文件中的选择,不会自动应用或认证这些记录;重新审校
可获取新的报告。
桌面端目前不提供公共 Web 的完整选择确认流程。保存失败时界面会说明失败,不会把未保存的更改
标记为已保存;无法读取的文件不会替换当前正文。

如果正文修改后多条历史选择落到了同一处,保存时会显示包含原文上下文和选择内容的冲突列表。
逐条选中不再需要的记录并按「移除选中的冲突选择」,直至冲突解除后再保存;移除可撤销或重做,
其他选择和历史报告会保留。

当前稿件有未保存的更改时,新建、打开另一份稿件或关闭窗口会先询问保存、放弃或取消。
取消操作或保存失败时,当前稿件保留在窗口中。

#### 文件拖入、剪贴板与最近打开

- **拖入文件。** 一次只能拖一个文件。`.txt`、`.md` 按 UTF-8 文本(允许 BOM,不超过 1 MiB)
  读入,整段替换你拖到的那一侧(拖到译文栏替换译文,拖到原文栏或其他位置替换原文),
  作为一次可撤销的编辑,不改变当前稿件的文件路径,稿件变为未保存。`.json` 按稿件文件打开,
  与「打开稿件」走同一条流程(未保存的改动会先询问)。多个文件、其他扩展名、不是 UTF-8、
  过大的文件,只在状态栏提示原因,不改动任何内容。输入法编辑中不接受拖入。
- **剪贴板。**「编辑」菜单里的「粘贴为原文」「粘贴为译文」用剪贴板文本整段替换对应一侧
  (可撤销,剪贴板为空则不改动);「复制译文」(Ctrl+Shift+C)把译文原样复制出去,保留换行
  符;「文件」菜单的「从剪贴板新建」新建稿件并把剪贴板文本放进原文。
- **最近打开与上次位置。**「文件 → 最近打开」列出最近 10 个稿件文件,文件已不存在的条目
  灰显并标注,可用「移除不存在的条目」清掉。重新打开某个文件时,会回到你上次离开时的光标、
  两栏滚动位置、右侧面板宽度,以及选中的语义疑点(重新审校出同一条疑点时才会选中,且不会
  覆盖你已经做出的选择)。位置只在保存、离开该稿件(打开另一个、新建)和关闭窗口时记录,
  不会在输入时写盘。
- **路径存在哪里。** 最近打开的完整路径以明文只存在 `%APPDATA%\WuwaTerm\config.json`
  里,从不写进稿件文件、导出结果、日志或任何请求。「文件 → 最近打开 → 清除最近文件」会
  清空这份记录。设置文件已损坏、读不出来时,最近列表只留在本次运行里,不会写盘覆盖那个文件,
  里面的服务器地址仍可以手工修复。

### 翻译结果:这条答案是哪来的

译文旁边有一枚徽章,用**形状、颜色、文字三重**标示来源,任何一种编码单独失效
(色觉障碍、灰度截图)都还能分辨:

| 徽章 | 含义 |
| --- | --- |
| 实心圆点 · 绿 | 词典精确匹配 |
| 空心圆环 · 琥珀 | 词典模糊匹配 |
| 圆角方块 · 蓝 | 模型翻译 |
| 横杠 · 灰 | 无需翻译 |

如果这次翻译没有匹配到任何官方术语,会**再加**一枚琥珀色徽章(「未匹配官方术语」),
并在译文下方说明该结果不具权威性。它是附加信息,永远不会替换掉来源徽章。

结果块最下面单独一行是请求 ID,右侧可一键复制。**成功和失败用的是同一个控件、同一个
位置** —— 出了事要拿什么去问运营方,不该因为成败而换地方。

### 出错的时候不会弹窗打断

失败以三种方式就地呈现,取决于错在哪里:

- **区域提示条**:这次请求失败了(连不上、超时、服务端错误、模型不可用或额度用尽、
  请求过密、凭据被拒),附带「重试」或「输入新令牌」。
- **字段提示**:错在你刚填的那一格(请求不合法、文本过长、内容过大),输入框描边转红,
  下方一行说明,焦点回到该格。
- **全局提示条**:跨区域的事实(尚未配置地址、地址不受保护、设置没能写盘)。

加载中永远是顶部一条细进度线加一行状态文字,不是遮罩,也不是模态。取消不是错误,
它只在状态行留一句话,不着红色。

普通请求错误不使用模态对话框。需要选择文件时使用系统文件对话框;关闭、打开或新建稿件
可能丢失未保存内容时要求保存、放弃或取消。遗忘令牌确认和「关于」对话框仍然保留。

### 外观

「设置 → 外观」有三档:跟随系统、亮色、暗色。默认跟随系统,系统主题切换时窗口会跟着变;
选定亮色或暗色之后,系统再变也不会顶掉你的选择。这个偏好存在 `config.json` 里。

界面只用 Windows 自带字体(微软雅黑 UI、Segoe UI、宋体等),不下载任何字体或图标资源,
图标及其许可随程序一同分发 —— 客户端在本机自足,离线可用。

## 配置服务器地址

「设置 → 服务器地址」只接受一个值:服务发布所在的那个受保护端点的基地址。网络路径的其他
一切都是部署方的事 —— 这个客户端只对你给的地址发 HTTPS 请求,而且接口契约里不编码任何
路径信息,所以改变服务的发布方式,在这里只需要改这一个字符串。

**没有默认地址。** 全新安装,以及任何一次读不到设置文件的启动,都从**未配置**状态开始:
状态芯片写「未配置」,顶部有一条不可关闭的提示条说明不会发出任何请求,当前区域给出
三步清单(填地址 / 录令牌 / 开始查询),每一步标出是否已完成。此时提交按钮是灰的,
自动查询也不会启动。早先的版本会在设置丢失时悄悄换上一个本机开发地址,于是「你的设置没了」
被显示成「服务器连不上」—— 一个对错误问题给出的确信回答。地址配好之后,那一行就写明它是谁。

只接受两种形式,没有第三种:

- `https://<主机>[:<端口>][/<路径前缀>]` —— 任何主机。每次请求都会验证服务器证书,
  始终如此。这个程序里没有任何设置、命令行参数或环境变量能把验证关掉。
- `http://127.0.0.1:<端口>`(或 `localhost`/`::1`)—— **仅限本机**,用于跑在你自己电脑上的
  开发服务。数据不离开本机,也就没有需要在传输中保护的东西。

设置字段空着时显示的 `https://example.com/wuwaterm-api` 只是一个中性示例,不会替你填上,
你不输入它就永远不会被使用。它刻意不再是本机开发地址:那个地址正是早先版本在设置丢失时
悄悄替换上去的那一个,把它摆在空字段里等于把刚删掉的建议又递回给正在决定填什么的人。

指向其他主机的明文 `http://` 会被拒绝 —— 在设置对话框里拒绝一次,在传输层构建请求之前
再拒绝一次:设备令牌在每一次调用中都随请求头发出,而手工输入或编辑的地址,正是它可能
以明文穿过网络的那条路。被拒绝时**不会半应用**:超时、地址和磁盘上的文件都不会被改动,
对话框保持打开,错误就写在出错的那一格下面。

端口由部署方配置(`WUWATERM_API_PORT`,默认 8788),这是在和本机服务通信时;
对于已发布的端点,地址以运营方给你的为准,通常就是一个主机名。

> Operations note: SSH is how an operator administers the server host. It is
> not part of this client's path to the service and never a requirement for
> using it — the application starts no such process, manages no keys, and
> needs nothing running beside it. See the [service deployment guide](https://github.com/My-Denia/WuwaTerm/blob/main/docs/deployment.md).

## 设置存在哪里

非机密的设置 —— 服务器地址、两个超时、外观偏好,以及最近打开的稿件列表(含完整路径和上次位置) —— 存在
`%APPDATA%\WuwaTerm\config.json`。那是**漫游**用户配置目录,重启后仍在,也不是临时位置。
设备令牌不在这个文件里,从来也没有过;它在 Windows 凭据管理器中。

- **一次保存不会留下写了一半的文件。** 它先在同一目录写一个临时文件,刷盘,然后一步
  替换掉设置文件;设置文件从不以截断方式打开。被中断的保存因此只会留下完整的旧文件或
  完整的新文件,不会留下截断的那种 —— 客户端会把截断的文件判定为不可用,而那样丢掉的
  是服务器地址。这说的是被中断的**写入**,不是断电之后磁盘盘片上还剩什么的断言。
- **文件不会被自动重建。** 如果它被删掉(手动删,或被磁盘清理工具删),客户端会以未配置
  状态启动并在界面上说明;在设置里重新填一次地址,它就会被写回。这不是假想:2026-08-12
  这个文件就在一次 Windows 重启后从机主的机器上消失了,而存好的设备凭据毫发无伤。
- **手工编辑过的文件会被校验,而不是被信任。** 客户端不会使用的地址、它解析不了的地址,
  或者读不懂的 JSON,都会让客户端停在未配置状态;超出 1–600 秒的超时会被夹到范围内,
  非数字的超时回落到默认值;无法识别的外观取值回落到「跟随系统」。这个文件里的东西,
  没有一样能不经检查就到达 HTTP 层。

## 超时、重试与重连

没有需要维持的后台连接,也就没有什么需要重连:每个动作按需打开一个 HTTP 请求,经由共享的
连接池化 `httpx` 客户端发出,响应到达即结束。连接会被池化复用;当池中的连接已被对端关闭时,
下一个请求会新建一条。

- **两个超时,都可配置。** `request_timeout_seconds`(默认 10 秒,设置 → 请求超时)用于
  术语查询与状态刷新;`translate_timeout_seconds`(默认 60 秒)用于 `POST /v1/translations`,
  因为它可能在等一个翻译模型。来自设置对话框和手工编辑的配置文件的值都会被夹到 1–600 秒。
- **它们是分阶段的限额,不是总的截止时间。** `httpx` 把这个值分别应用到连接、写入、读取
  和等待池中连接上,所以它约束的是**没有进展**的等待时长,而不是整个调用的挂钟时间:
  一个持续在传字节的对端,可以合法地把请求保持得比这个数字更久。服务端本身不是这样 ——
  它按真实流逝时间执行自己的截止并回答 504 —— 所以一个以这种方式跑很久的调用,说明问题
  在这台电脑和服务之间,而不在服务本身。
- **在出厂默认值下,哪个先到期。** 客户端 60 秒的翻译超时短于服务端自己的请求截止
  (`WUWATERM_API_REQUEST_TIMEOUT_SECONDS`,默认 90 秒),所以一个单纯耗时过长的翻译会以
  客户端超时收场,而不是服务端的 504。只有当你把客户端的翻译超时调到它之上时(客户端允许
  到 600 秒),服务端的截止才会成为先到期的那个。
- **超时会被报告,绝不自动重试。** 请求停止,界面显示「请求超时」。这个客户端不自动重试:
  一个已经到达服务的翻译请求可能已经花掉了模型额度,而悄悄再发一次不是一个程序该替你做的
  决定。再按一次按钮就是一次新的请求。
- **连不上服务。** 连接失败会被报告为「无法连接到服务器…」,客户端仍然可用;下一次请求从头
  再来。这次失败不会缓存任何状态。
- **取消停下的是等待,不是工作。** 翻译 → 取消结束的是这个客户端的这次请求:状态行说明请求
  已被取消,按钮回到常态。它是否还停下了别的什么,取决于它落得多早。在请求还在交付途中时
  —— 等连接、正在连接、正在发送 —— 服务端手上还没有一个完整的请求可以处理,所以什么都没被
  翻译,也没有花费。一旦它拿到了完整的请求(而你的文本很短,所以这个窗口很短),取消就不再
  能够触及服务端:它不会被告知你不等了,它会把这次请求做完,并按一次普通的完成来记录。
  如果这次请求需要翻译模型,那次模型调用会跑到底并被计费,无论你是否还在等;而词典命中根本
  不会走到模型那一步,无论如何都不花钱。这时取消让程序腾出手来,但没有停下那份工作,也没有
  退回请求已经承诺出去的任何开销。答案被读都不读地丢弃,请求 ID 也随之丢弃,所以这样的一次
  请求事后无法拿去向运营方查询。再按一次翻译是一次新的请求,而到达模型的那一次会再付一次钱。

以下英文说明保留相同的取消语义:

> **Cancellation stops the waiting, not the work.**
> While the request is still being handed over, the service does not yet have a whole request to act on, so nothing is translated and nothing is spent.
> Once it does have the whole request, Cancel no longer reaches the service: it finishes the request and records it as an ordinary completed one.
> Cancelling then frees the application without stopping the work, and without un-spending anything the request had already committed.
> If that request needed the model, the model call is paid for whether or not you are still waiting; a dictionary hit never reaches the model and costs nothing either way.

## 获取与保存设备凭据

没有自助注册界面,服务端也从不生成或打印凭据材料。服务的运营方生成一个密钥,用
`wuwaterm-api device issue`(从标准输入读取该密钥)把它登记到某台设备上,然后通过带外渠道
把得到的令牌交给你。令牌形如 `wtd1.<设备 id>.<那个密钥>`;服务端只保存该密钥加盐后的
scrypt 验证值,所以事后没有人能从服务端把令牌还原出来 —— 一旦丢失,运营方吊销那台设备并
重新登记一台。

密钥至少 32 个可打印 ASCII 字符且不含空格,所以令牌总是可以整行粘贴的一行。
从「设置 → 输入 / 更改令牌」把它粘进去即可。旁边的「显示」可以切换明文,便于核对
首尾。令牌为空时「继续」不可点。客户端会立即把它存进 Windows 凭据管理器,并且不再显示它。
如果凭据管理器当时不可用,对话框会就地说明并保持打开,可以重试 —— 不会因此把程序关掉。

设备令牌与服务器地址分开保存，也可能分别缺失。未配置时仍可处理本地稿件；
在线操作会说明需要补齐的服务或凭据信息，不在启动时强制收集。

## 删除已保存的凭据

「设置 → 遗忘令牌」会把凭据从 Windows 凭据管理器中删除,并要求确认一次,因为它不可撤销。
你也可以直接从 Windows 删除:打开凭据管理器 →
Windows 凭据,找到 WuwaTerm 条目并删除。

## 构建与测试

在 Windows 的仓库根目录中，安装 Python 3.12 和 uv 后运行：

.venv\Scripts\python.exe -m pytest

测试使用模拟 HTTP 和内存凭据存储，不访问真实服务或 Windows 凭据管理器。独立运行纯稿件文件测试无需 Qt 或 keyring：

python -m pip install pytest
$env:PYTHONPATH = "src"
python -m pytest tests/test_manuscript.py

跨产品契约测试还需 Node 及 [固定的 Core 和 Web 源码](contracts/sources.json)，通过 `WUWATERM_CORE_ROOT` 和 `WUWATERM_WEB_ROOT` 指向对应目录。源码文件哈希与记录不符会失败；设置 `WUWATERM_CONTRACTS_REQUIRED=1` 后，缺少源码或 Node 也会失败。CI 强制执行 Core API 和 Web 双向稿件测试。

## 依赖漏洞门禁

`.github/workflows/dependency-audit.yml` 审计 `uv.lock` 锁定的依赖集合：critical 和 high 的 advisory（漏洞公告）让 CI 失败，medium 和 low 只打印。它回答的是 `uv sync --locked` 不回答的问题——锁能解析、与 `pyproject.toml` 一致、构建装的确实是锁里的版本，这些都不说明某个固定版本有没有已披露的漏洞。

### 审计的对象

门禁用与 `windows-build.yml` 相同的 uv 导出已提交的锁：

```powershell
uv export --frozen --format requirements-txt --no-hashes --all-extras --no-emit-project > requirements-locked.txt
```

`--frozen` 只读 `uv.lock`，不重新解析；`--all-extras` 把 dev 和 build 两组依赖一并导出；`--no-emit-project` 排除本项目自己。导出为空或被截断是这门禁最怕的假绿，所以审计之前先检查 `pyside6`、`httpx`、`keyring`、`qasync`、`pyinstaller`、`pytest` 都在，缺一个就失败。

`pip-audit` 固定 `2.10.1`，用 `--no-deps` 只读这份锁定清单。它为 `-r` 建的临时环境里已经装了 `pip`、`wheel`、`setuptools`、`packaging`，被 pip 判为“已满足”的锁定项不进报告；门禁把这四项单列为只警告、不失败（当前是 `packaging` 和 `setuptools`），每次运行都写清自己没读到什么。四项之外，导出里有而报告里没有的锁定项算覆盖不全，判为不可信。对账还要求导出的每一行都能读成“名称==版本”加可选的环境标记，读不出来同样不可信。

### 什么会让它失败

- critical 或 high 漏洞。
- 读不出严重级别。`pip-audit` 不报严重级别，门禁从 OSV 记录读 GitHub 的标签（`database_specific.severity`），优先查 `GHSA-` 编号，同一漏洞的多条记录合并成一条。查不到级别的按阻断处理：没人能分类的版本不算干净证据。只有 `pip-audit` 真找到漏洞时才请求 OSV，干净的一次运行不发请求。
- 报告不可信：文件缺失、为空、截断或不是合法 JSON；有依赖 `pip-audit` 没能收集；`pip-audit` 的退出码不是 0 或 1，或者退出码是 1 而报告里没有漏洞。这几种都以 exit 2 结束。

medium 和 low 会带编号和修复版本打印出来，不失败。处理办法是抬高 `pyproject.toml` 里的下限，或给传递依赖加约束，并记录这条漏洞为什么不适用；把门禁改绿不算。

### 什么时候跑

推送到 `main`；改了依赖输入的 PR（`pyproject.toml`、`uv.lock`、判据脚本及其测试、这个 workflow 本身）；每周一 04:37 UTC 的定时运行；手动 dispatch。漏洞是针对不会变的版本发布的，一周没有提交也可能变红。

它刻意不是 `ci.yml` 里的 job，也不要设成 required status check。`pull_request.paths` 是 workflow 级过滤，不碰依赖文件的 PR 根本不会启动它；设成 required check，这类 PR 就会永远等一个不会出现的状态。挂进 `ci.yml` 则会让不碰依赖的 PR 跳过测试矩阵和 Windows 构建，让每周的定时运行顺带构建 EXE 和发布 ZIP，而 `ci.yml`、`windows-build.yml` 的 job 名是 `release.yml` 校验过的来源，加 job 会改变发布运行时看到的东西。

### 它明确不覆盖什么

- 只在 Windows 上生效的锁定项。审计跑在 Linux runner 上，`sys_platform == 'win32'` 的 3 项（`colorama`、`pefile`、`pywin32-ctypes`）和 `sys_platform == 'darwin'` 的 1 项（`macholib`）按标记排除，不计入覆盖缺口；本地在 Windows 上跑时，覆盖范围按本机平台重新计算。
- PyInstaller 打进 `WuwaTerm.exe` 的第三方代码：门禁只看 PyPI 上的发行版，不看可执行文件内部。
- 非 PyPI 来源：`contracts/sources.json` 固定的 Core、Web 源码和 Node 契约工具链不在审计范围内。
- 审计之后才发布的漏洞，由下一次定时运行发现。

### 本地怎么跑

在仓库根目录，PowerShell 7（`pwsh`，与 `build.ps1` 相同；Windows PowerShell 5.1 的重定向默认写 UTF-16，判据脚本会拒绝这个文件）：

```powershell
uv export --frozen --format requirements-txt --no-hashes --all-extras --no-emit-project > requirements-locked.txt
foreach ($name in 'pyside6','httpx','keyring','qasync','pyinstaller','pytest') {
  if (-not (Select-String -Path requirements-locked.txt -Pattern "^$name==" -Quiet)) { throw "requirements-locked.txt is missing $name" }
}
uv run --no-project --python 3.12 --with pip-audit==2.10.1 python -m pip_audit -r requirements-locked.txt --no-deps --strict --progress-spinner off --format json -o pip-audit.json
$status = $LASTEXITCODE
uv run --no-project --python 3.12 --with pip-audit==2.10.1 python scripts/check_dependency_advisories.py pip-audit.json --audit-exit $status --export requirements-locked.txt
```

判据脚本要在带 `pip-audit` 的环境里跑，因为对账要用 `packaging` 解析环境标记；用裸 `python` 会报错。`requirements-locked.txt` 和 `pip-audit.json` 没有进 `.gitignore`，跑完删掉。

### 失败时看哪里

job 名是 `locked dependencies (critical/high)`。每条阻断的漏洞会有一条注释，写明包名、漏洞编号和修复版本。成功和失败都会上传 `dependency-audit-report-<run_attempt>`，内容是 `pip-audit.json` 和 `requirements-locked.txt`；名字带 attempt 号，重跑才不会和上一次的上传撞名。

## 发布

`release.yml` 手动构建指定的完整 main 祖先提交，要求该提交在 `main` 上的 CI 完整成功——`push` 运行，或对同一提交手动 dispatch 的 `ci.yml` 运行；默认只构建，取消 dry run 才创建草稿。只改 `README.md`、`README.*.md`、`CHANGELOG.md`、`docs/**`、`provenance/**` 的提交不启动 `ci.yml`，因为这类改动到不了运行时、契约、依赖和打包出的 exe；发布必须改 `pyproject.toml` 和 `src/wuwaterm_client/__init__.py` 里的版本，这两个文件不在跳过清单里，所以发布源码总有自己的一次完整运行。因此不要把 `ci.yml` 的 job 设成 required status check：只改文档的 PR 不会启动它，设了就会永远等一个不会出现的状态。需要时可以用 `workflow_dispatch` 对 `main` 手动跑整套 CI。草稿包含 ZIP、`SHA256SUMS` 和记录版本、源码提交、ZIP 哈希及未签名状态的 manifest。检查产物及实际 Windows 启动后，再单独发布草稿。发布草稿和构建是两个步骤。
